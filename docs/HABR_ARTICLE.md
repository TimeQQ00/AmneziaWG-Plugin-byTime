# VPN внутри мессенджера: пишем AmneziaWG-туннель для exteraGram без VpnService

*Как собрать собственное ядро AmneziaWG под Android, загрузить его в Python-плагин
и направить трафик Telegram в обфусцированный туннель — не поднимая системный VPN.*

---

## Вступление: зачем это вообще

Задача звучала просто: «нужно, чтобы Telegram работал даже при блокировках,
без отдельного VPN-приложения». Обычные решения не подходили:

- **Системный VPN** — отдельный APK, разрешение `VpnService`, постоянное
  уведомление, конфликты с другими VPN, весь трафик телефона через туннель.
- **SOCKS5-прокси** в настройках Telegram — поднять некому: нужен сервер
  с obfuscated-протоколом, иначе прокси убивается DPI за часы.
- **Публичные MTProto-прокси** — живут недолго и небезопасны.

Так родилась идея: сделать **плагин для exteraGram, внутрь которого встроен
сам туннель**. Никаких системных служб: движок — это разделяемая библиотека
внутри процесса мессенджера, а «точкой входа» трафика служит локальный SOCKS5,
к которому Telegram стучится как к обычному прокси.

В итоге получился плагин **AmneziaWG byTime**: 10.3 МБ, без root, без
разрешений VpnService, с импортом пользовательских `.conf` и живым тестом
туннеля перед подключением. Под капотом — собственное ядро на Go (7.4 МБ),
gVisor-стек в userspace и связка с внутренними API Telegram.

Ниже — весь путь по техническим решениям.

---

## 1. Почему AmneziaWG, а не WireGuard

AmneziaWG — это форк WireGuard, заточенный под обход DPI. Формально это тот же
протокол с теми же крипто-примитивами (ChaCha20-Poly1305, Curve25519), но в
рукопожатие и транспорт добавлены «нестандартные» вещи, которые ломают
сигнатуры протокола:

| Параметр | Смысл |
|---|---|
| `Jc`, `Jmin`, `Jmax` | вставка «мусорных» пакетов перед рукопожатием |
| `S1`–`S4` | размер padding'а для разных типов пакетов |
| `H1`–`H4` | замена «магических» заголовков типов сообщений |
| `I1`–`I5` | сигнатуры-обфускаторы (специальные байтовые цепочки в начале потока) |

Для DPI это уже не WireGuard: характерные первые байты пакетов заменены,
а перед реальным рукопожатием летят случайные данные.

В моём конфиге:

```ini
Jc = 4
Jmin = 40
Jmax = 70
H1 = 1  H2 = 2  H3 = 3  H4 = 4
I1 = <b 0xce000000010897a297...   # ~2.5 КБ сигнатуры
```

`I1` — самое интересное: это цепочка длиной около **2500 символов**, которая
добавляется в поток. Ядро `amneziawg-go` версии 3.x понимает её в формате
`<b 0x...>`, и передаётся она через тот же uapi-интерфейс, что и обычные
WireGuard-ключи.

## 2. Ключевая идея: userspace-туннель + локальный SOCKS5

Обычное VPN-приложение устроено так: TUN-интерфейс → ядро ОС → маршрутизация.
Это сразу тянет за собой `VpnService`, `Builder.establish()`, файловые
дескрипторы и системные разрешения.

Я пошёл другим путём: **сетевой стек целиком в userspace**.

```
Telegram (TCP)
      │  SOCKS5 на 127.0.0.1:10809
      ▼
┌─────────── libawgcore.so ────────────┐
│  go-socks5 (сервер)                  │
│        ▼                             │
│  gVisor netstack  ← TCP/IP без ядра  │
│        ▼                             │
│  amneziawg-go    ← шифрование + UDP  │
└──────────────────────────────────────┘
      │ UDP в обычный сокет процесса
      ▼
  AmneziaWG-сервер
```

Что это даёт:

- **Нет `VpnService`** — не нужны разрешения, нет постоянного уведомления,
  нет конфликта с другими VPN.
- **Нет TUN** — вместо него gVisor-стек: TCP-соединения создаются прямо в
  памяти процесса, для системы это обычные сокеты, которые пишет Telegram.
- **Нет root** — всё в рамках песочницы приложения.

Цена: туннель работает только для того, кто в него ходит. В нашем случае это
идеально — ходит только Telegram.

## 3. Движок: три библиотеки и три C-функции

Ядро собрано из:

| Библиотека | Роль |
|---|---|
| `amnezia-vpn/amneziawg-go/v3` | протокол AmneziaWG |
| `gvisor.dev/gvisor` (netstack) | TCP/IP в userspace |
| `things-go/go-socks5` | SOCKS5-сервер |

API наружу — три функции:

```c
int awgStart(const char *configJson);  // 0 = ok, -1 = плохой JSON, -2 = ошибка старта
int awgStop(void);
int awgStatus(void);                   // 1 = работает
```

Внутри `awgStart` происходит:

```go
tun, tnet, _ := netstack.CreateNetTUN(localAddresses, dnsServers, mtu)
dev := device.NewDevice(tun, conn.NewDefaultBind(), device.NewLogger(level, "awg"))
dev.IpcSet(ipcConfig)   // private_key, endpoint, allowed_ip,
                        // jc/jmin/jmax, s1..s4, h1..h4, i1..i5
dev.Up()
listener, _ := net.Listen("tcp", "127.0.0.1:10809")
server := socks5.NewServer(socks5.WithDial(tnet.DialContext), ...)
go server.Serve(listener)
```

Две детали, на которые стоит обратить внимание.

**DNS уходит в туннель.** В go-socks5 обработчик CONNECT вызывает
`dial(ctx, "tcp", request.DestAddr.String())` — то есть **имя хоста передаётся
как есть**, если задан кастомный dialer. Тонкость: у go-socks5 есть и встроенный
резолвер, который вызывается **до** dialer'а и при дефолтных настройках разрешил
бы FQDN средствами Android — DNS-запрос ушёл бы мимо туннеля. Поэтому в движке
задан passthrough-резолвер (`Resolve` возвращает IP = nil), после чего
`AddrSpec.String()` честно возвращает FQDN, и доменное имя доходит до
gVisor-стека, а тот резолвит его через DNS-серверы из конфига (`1.1.1.1`).
Это и правильно, и быстрее.

**Keepalive обязателен.** По умолчанию ставлю 25 секунд: мобильные сети
безжалостно убивают NAT-сессии, и туннель «умирает» через минуту простоя.

### Сборка под Android

Тут было два приключения.

**Первое — компилятор.** Для `-buildmode=c-shared` под `android/arm64` нужен
C-тулчейн. `zig` последних версий перестал поставлять bionic-заголовки
(`unable to provide libc for target aarch64-linux-android`), а старые версии
не подошли по другим причинам. Решение — честный **Android NDK r25c**:

```powershell
$env:GOOS='android'; $env:GOARCH='arm64'; $env:CGO_ENABLED='1'
$env:CC='...android-ndk-r25c\...\bin\aarch64-linux-android21-clang.cmd'
go build -trimpath -ldflags "-s -w" -buildmode=c-shared -o libawgcore.so .
```

Результат — 7.4 МБ, ELF64, `arm64`, `ET_DYN`, зависимости только от
`libc.so`, `liblog.so`, `libdl.so` (всё есть на любом Android).

**Второе — проверка.** Запустить arm64-библиотеку на ПК нельзя, поэтому я
собрал **вторую, тестовую сборку под Windows** (`zig cc -target x86_64-windows-gnu`)
и прогнал через неё живой тест — об этом в разделе 6.

## 4. Как загрузить .so в Python-плагин (и почему Android это разрешает)

exteraGram-плагины — это Python (Chaquopy, CPython 3.11) внутри Android-приложения,
с доступом к Java-классам через `jclass`. Значит, нативный движок надо
подгрузить через `ctypes`:

```python
lib = ctypes.CDLL("/data/data/<pkg>/app_awgcore/libawgcore.so")
lib.awgStart.argtypes = [ctypes.c_char_p]
lib.awgStart.restype = c_int
lib.awgStart(json.dumps(cfg).encode())
```

Тут есть известная «страшилка»: **Android 10+ не даёт приложениям выполнять код
из своей песочницы**. Действительно, с API 29 запрещён `execve()` файлов из
домашнего каталога приложения — именно из-за этого Termux застрял на
`targetSdk 28`.

Но запрет касается **запуска исполняемых файлов**, а не `dlopen()`. По
SELinux-политике домен `untrusted_app` (обычные приложения, включая мессенджеры)
имеет право `execute` на файлы `app_data_file`. Поэтому загрузка `.so` из
приватного каталога приложения работает и на Android 10, и на 14 — главное,
чтобы файл был читаемым и имел флаг исполняемости.

Практическая схема (её же использует известный плагин exitFy, я разбирал его
DEX для сверки):

1. `.so` лежит внутри самого `.plugin`-файла, в base64-блоке (ничего не
   докачивается из сети).
2. При первом запуске пишется в `context.getDir("awgcore", 0)` —
   это приватный каталог приложения.
3. Запись атомарная: временный файл → `fsync` → `chmod 700` → `os.replace`.
4. Сверка sha256: если файл уже есть и совпал — не перезаписываем.
5. `ctypes.CDLL(path)` — и движок в памяти.

Отдельный приятный момент: JNI-обвязка не нужна вообще. `-buildmode=c-shared`
экспортирует обычные C-функции, а `ctypes` вызывает их напрямую.

## 5. Как направить Telegram в свой SOCKS5

Самое интересное. Telegram (и его форк exteraGram) умеет прокси, но как
включить его программно?

Читаем исходники Telegram и разбираем DEX плагина exitFy (отличный источник
знаний по внутреннему API). Схема из трёх шагов:

```python
# 1) добавить прокси в список Telegram и сделать активным
info = SharedConfig.addProxy(ProxyInfo("127.0.0.1", port, "", "", ""))
SharedConfig.currentProxy = info

# 2) переключить сетевой стек на этот прокси
ConnectionsManager.setProxySettings(True, "127.0.0.1", port, "", "", "")

# 3) записать флаг в настройки и уведомить UI
MessagesController.getGlobalMainSettings().edit() \
    .putBoolean("proxy_enabled", True).apply()
NotificationCenter.getGlobalInstance().postNotificationName(
    NotificationCenter.proxySettingsChanged)
```

После этого Telegram сам поднимает все свои соединения (MTProto, медиа,
превью) через `127.0.0.1:10809` — то есть через наш движок.

**Грабли совместимости.** В новых версиях Telegram API изменился: появился класс
`org.telegram.proxy.ProxySettings` (builder-стиль), а `setProxySettings`
принимает объект вместо шести аргументов. Чтобы плагин не падал на разных
сборках exteraGram, я делаю так: сначала пробую старый API, при исключении —
новый:

```python
try:
    info = ProxyInfo("127.0.0.1", port, "", "", "")
    ConnectionsManager.setProxySettings(True, "127.0.0.1", port, "", "", "")
except Exception:
    settings = ProxySettings.builder().setAddress("127.0.0.1") \
        .setPort(port).setUser("").setPassword("").setSecret("").build()
    info = SharedConfig.addProxy(SharedConfig.ProxyInfo(settings))
    ConnectionsManager.setProxySettings(True, settings)
```

Одна тонкость: `jclass("org.telegram.proxy.ProxySettings")` нельзя вызывать на
верхнем уровне модуля — если класса нет, плагин не загрузится вообще. Поэтому
новый API импортируется **лениво**, внутри `except`.

## 6. Тестирование: как проверить arm64-туннель, не имея телефона

Запустить arm64-библиотеку на ПК нельзя. Поэтому — **двойная сборка**: тот же
исходник компилируется под Windows (`zig cc -target x86_64-windows-gnu`), и
тест гоняет реальный туннель на десктопе.

Скрипт `test_e2e.py` делает всё по-настоящему:

```python
lib.awgStart(json.dumps(cfg).encode())        # поднимаем туннель
s = socks_connect("example.com", 80)          # SOCKS5 через движок
s.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n")
# => b"HTTP/1.1 200 OK"
```

Результат первого прогона — и он же ответ на вопрос «а вдруг я неправильно
передаю обфускацию»:

```
peer(bmXO…fgyo) - Sending handshake initiation
peer(bmXO…fgyo) - Received handshake response     ← рукопожатие с сервером прошло
socks port open: True
received 869 bytes: HTTP/1.1 200 OK
E2E RESULT: PASS
```

Этот тест проверяет сразу всё: парсинг конфига, передачу `Jc/Jmin/Jmax/S1-S4/H1-H4`,
разбор `I1`-сигнатуры, gVisor-стек, SOCKS5-сервер и реальный обмен данными с
сервером на другом конце.

Второй тест — `test_plugin_logic.py` — подгружает сам код плагина со стабами
exteraGram-модулей и проверяет парсер `.conf`, выбор активного конфига и
функцию проверки туннеля. Такая проверка ловит опечатки до установки на телефон.

Кстати, именно тест поймал реальный баг: в SOCKS5-ответе сервер присылает
адрес и порт **после** первых четырёх байт, и мой код читал первые 16 байт
вместе с «хвостом» — проверка `startswith(b"HTTP/")` всегда падала. Исправил,
и `verify_tunnel` стал честной проверкой «туннель реально пропускает трафик».

## 7. Пользовательские конфигурации: «свой сервер» в два тапа

Плагин поставляется без встроенного сервера: пользователь подключает свой
конфиг — это осознанное решение, приватные ключи не должны распространяться
с приложением. Реализовано так:

1. В настройках плагина — кнопка **«Выбрать .conf на устройстве»**: плагин
   сканирует `Download`/`Documents` и показывает диалог выбора (если файл один —
   импортирует сразу). Есть ещё импорт из буфера обмена и ручной ввод пути.
   Все три ведут к «Импортировать и подключиться» (виджет `Text` с `on_click`).
2. Плагин читает файл в формате `wg-quick` и разбирает его регулярками:
   секции `[Interface]`/`[Peer]`, ключи `PrivateKey`, `Address`, `DNS`, `MTU`,
   `Jc/Jmin/Jmax`, `S1–S4`, `H1–H4`, `I1–I5`, `PublicKey`, `AllowedIPs`,
   `Endpoint`, `PersistentKeepalive`.
3. Конфиг сохраняется в настройках плагина, движок перезапускается.
4. **Главное:** перед тем как объявить успех, плагин проверяет туннель
   «в бою» — SOCKS5-подключение к `1.1.1.1:80` и ожидание ответа `HTTP/...`.
5. Если проверка не прошла — туннель корректно останавливается с понятным
   сообщением «проверьте конфиг». (В личной сборке со вшитым сервером плагин
   делает откат на встроенный конфиг — механизм тот же.)

Это важно, потому что криптографически неверный ключ или несовпадающие
obfuscation-параметры движок принимает **без ошибки** — туннель просто не
пропустит ни байта. Единственный надёжный способ это выявить — реальная
передача данных.

## 8. Жизненный цикл: почему «подключается — отключается — подключается»

Первая версия страдала классической болезнью: при каждом возврате в приложение
туннель пересоздавался, и в уведомлениях мелькало «Отключено → Подключено».
Причина — событие `RESUME` слишком агрессивно дёргало ядро.

Как исправлено:

```python
def _resume_check(self):
    # туннель жив и проверка трафика проходит — НЕ ТРОГАЕМ
    if ENGINE.status() and ENGINE.port_open() and ENGINE.verify_tunnel():
        return
    restart_tunnel()   # поднимаем только реально умершее
```

Плюс рекомендация для пользователя: «Батарея → Без ограничений» для Telegram.
Это единственный официальный способ не дать системе заморозить процесс —
никакие хаки в плагине этого не заменят.

## 9. Что получилось в цифрах

| Параметр | Значение |
|---|---|
| Размер плагина | 10.3 МБ (движок 7.4 МБ внутри, base64) |
| ОЗУ | ~30–60 МБ в процессе Telegram |
| Разрешения | ни одного сверх обычных прав Telegram |
| Системный VPN | не используется |
| Root | не нужен |
| Платформа | Android 10+, arm64-v8a |
| Порт SOCKS5 | 127.0.0.1:10809 (авто-выбор при занятости) |
| Keepalive | 25 секунд |

Что **не** работает и почему:

- **Звонки.** Они идут по UDP, а SOCKS5 туннелирует только TCP. Теоретически
  можно добавить UDP ASSOCIATE в SOCKS5 и прокидывать его в gVisor-стек, но
  это отдельная большая задача.
- **Всё остальное приложение телефона.** Это не системный VPN, и это осознанный
  выбор: меньше разрешений, ноль конфликтов, меньше батареи.

## 10. Чему я научился (короткий список грабель)

1. **`zig` больше не собирает под Android** из коробки — берите NDK.
2. **`dlopen` из data-каталога разрешён**, `execve` — нет. Не путайте.
3. **`jclass` несуществующего класса убивает плагин** на загрузке — ленивьте
   необязательные импорты.
4. **SOCKS5-ответ имеет «хвост»** — читайте адрес и порт, иначе разбор
   следующего пакета поедет.
5. **Тестовая сборка под десктоп окупается**: живой E2E на Windows нашёл
   ошибки до установки на телефон.
6. **Неверный AWG-конфиг не даёт ошибки** — проверяйте туннель данными,
   а не статусом.
